Tu web puede pasar meses sin dar problemas y, un lunes, dejar de enviar el formulario de contacto. Hay dos maneras de prepararte para ese día. Una es arreglar el fallo cuando aparece. La otra, revisar la web con un calendario para encontrarlo antes.

Las dos tienen sentido en algún momento. Lo que las separa es quién detecta el problema y con cuánto margen se resuelve. ¿Lo ve la persona que cuida la web o un cliente que no consigue escribirte?

## Lo que el mantenimiento reactivo hace bien

Para algunas webs es una opción razonable, al menos durante un tiempo:

- **Sin cuota fija.** Solo se paga cuando hay que intervenir.
- **Sin compromiso continuo.** Se encarga de forma puntual, cuando aparece el problema.
- **Suficiente en webs sencillas**: informativas, que cambian poco y no generan contactos ni ventas.

Su límite es el momento en que se actúa. El aviso suele llegar de fuera. Puede ser un navegador que muestra un certificado caducado o un correo del proveedor de alojamiento. También puede ser un cliente que te llama para preguntar si recibiste su mensaje de la semana pasada. Así descubres que el formulario lleva días sin enviar nada. A partir de ahí, todo se hace con prisa.

## Lo que aporta el mantenimiento preventivo

Un [mantenimiento preventivo](/diseno-programacion-web/mantenimiento-web-para-empresas/) no elimina los imprevistos. Cambia cuándo aparecen y cómo se resuelven:

- **Detección en la revisión, no en la queja.** Un plugin incompatible, un certificado a punto de caducar o una copia incompleta salen en la revisión programada.
- **Actualizaciones al día y probadas**, en lugar de acumularse durante meses. Cuantas más se juntan, más difícil es aplicarlas sin conflictos. El método paso a paso está en [actualizar WordPress tú mismo o con mantenimiento profesional](/recursos/actualizar-wordpress-tu-mismo-o-con-mantenimiento-profesional/).
- **Copias que se sabe que funcionan.** Se guardan en otro sitio y de vez en cuando se prueba a recuperarlas. Así puedes volver atrás con confianza.
- **Menos urgencias.** La mayoría de incidencias se resuelven en horario de trabajo y con calma, no con la web caída.

Al pasar de un enfoque a otro, lo habitual no es que dejen de pasar cosas. Es que dejan de ser urgencias. El certificado se renueva un martes cualquiera, no con el teléfono sonando.

## Cinco incidencias habituales, vistas desde cada enfoque

Ninguna de estas situaciones es rara ni grave por sí sola. La tabla te muestra cómo se descubre cada una según el enfoque.

| Incidencia | Con mantenimiento reactivo | Con mantenimiento preventivo |
|---|---|---|
| Certificado SSL a punto de caducar | Lo descubre el navegador del visitante | Se renueva antes de la fecha |
| Plugin con un fallo de seguridad ya publicado | Se corrige si alguien se da cuenta | Se actualiza en la revisión |
| Copia de seguridad que no se completa | Se descubre al intentar restaurar | Se detecta al comprobar las copias |
| Formulario que deja de enviar | Se nota cuando faltan contactos | Se ve en la prueba de formularios |
| Web cada vez más lenta | Se percibe cuando ya molesta | Se mide y se corrige por partes |

## Cómo decidirlo

| Criterio | Mantenimiento reactivo | Mantenimiento preventivo |
|---|---|---|
| Coste mientras no hay incidencias | Ninguno | Cuota periódica |
| Quién detecta el problema | Un visitante, el navegador o el alojamiento | La revisión programada |
| Momento de la intervención | Con la web ya afectada | Antes de que afecte, en la mayoría de casos |
| Actualizaciones | Se acumulan | Al día y probadas |
| Copias de seguridad comprobadas | Si alguien se ocupa | De forma sistemática |
| Tipo de web adecuado | Informativa, sencilla y con poco tráfico | Web que genera contactos, reservas o ventas |

Para decidir rápido:

- **Mantenimiento reactivo** si tu web es informativa, cambia poco y un día de caída no afecta al negocio.
- **Mantenimiento preventivo** si tu web genera contactos, reservas o ventas, o tiene formularios y áreas privadas de uso diario.
- **Un modelo mixto** al principio, con revisiones básicas de copias y actualizaciones. Luego las amplías a medida que la web gana peso en tu negocio.

Quién hace esas revisiones, tu equipo o un servicio externo, es otra decisión. Se analiza en [mantenimiento web propio o externalizado](/recursos/mantenimiento-web-propio-o-externalizado/). La misma lógica de revisar antes de que algo falle sirve para tus otros equipos y sistemas. La verás aplicada en [soporte IT reactivo o proactivo](/recursos/soporte-it-reactivo-o-proactivo/).
